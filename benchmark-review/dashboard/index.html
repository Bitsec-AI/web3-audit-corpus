How each requirement is measured, and what is missing
Function names
Functions named in the bug description, before any PoC test, mitigation or discussion: inline code, plain-text calls such as Vault.withdraw( or camelCase(, and functions defined or called in code snippets. Test helpers and language built-ins are left out.
Root cause
The corpus's own label: one class per finding from its taxonomy, assigned by an LLM from the title and first 3,000 characters. It names the earliest root cause, not the attack.
Attack path
A section headed Attack Path, Exploit Scenario, Steps to Reproduce or similar. Most reports describe the attack inside the main text, so this undercounts what an extraction pass could recover. The corpus gives every finding one root-cause class, not a set of attack vectors; building those sets needs a separate labelling pass.
PoC test
Test code in the finding: function test…(, #[test], vm.prank(…), forge test and similar.
Fix
A diff in the finding, or a link to a fix commit or pull request. A linked fix can be fetched as a patch.
Scope size
Sherlock nSLOC comes from Sherlock's contest API. Code4rena sizes come from each audit repo's README scope table: nSLOC where given, otherwise cloc code lines or listed file lengths, so older Code4rena sizes are approximate. Firm reviews have no scope size in the corpus.
Audited code
Sherlock's scope repo at the commit the contest used, or the Code4rena audit repo at its current default-branch commit. A private repo will not open.
